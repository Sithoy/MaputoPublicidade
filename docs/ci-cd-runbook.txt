Workflow
CI runs on main/staging pushes, codex/ci-* pushes, PRs to main/staging, merge
groups, manual dispatch, and a weekly schedule. Jobs have time limits, least
privilege permissions and pinned action revisions; superseded PR runs cancel.

Backend:
- PostgreSQL 16 service, isolated database, random per-run signing key.
- Ruff, Django checks, migration drift check and fresh migration application.
- Full pytest under branch coverage; enforced aggregate minimum 80%.
- Required PyMuPDF dependency; the document-content assertion no longer skips.
- JUnit and coverage reports retained for seven days.

Frontend:
- Node 24, matching Vercel's configured major version; npm ci with a lockfile.
- ESLint, TypeScript, full Vitest coverage and production build.
- Measured local baseline: lines 36.98%, statements 38.81%, functions 35.01%,
  branches 42.92%, across application, components, hooks and libraries.
- Initial global floors: lines/statements 35%, functions 30%, branches 40%.
  These prevent major regression, not evidence of adequate frontend coverage.
- Higher auth-proxy floors and 100% coverage floors for URL-boundary helpers.
- Generated coverage/browser reports are excluded from lint and Git.

Security:
- pip-audit --strict on requirements.txt (currently runtime and some test tools).
- npm production audit blocks high/critical dependency advisories.
- PR dependency review rejects newly introduced high/critical advisories across
  runtime, development and unknown scopes. Known pre-existing development risks
  are NOT silently claimed fixed by the production-only audit.
- CodeQL security-extended scans Python and JavaScript/TypeScript. A separately
  tested SARIF gate rejects high/critical/error findings, failed scans, missing
  reports and invalid severity values. A green scanner process alone is not enough.
- Gitleaks checks committed credentials, with comments, summaries and raw secret
  artifact uploads disabled. No blanket ignore policy is introduced.
- Dependabot proposes weekly npm, pip and GitHub Actions updates; it does not
  automatically approve or merge them.
- Snyk remains an additional tool, not a required secret-bearing CI dependency.
  CodeQL results are independent of the previous Snyk triage.

Browser acceptance:
- Chromium drives a production Next build against a real disposable backend.
- Registration, real API session, reload and subsequent password login.
- Private-library upload/read, denial to a second client, and deletion with 204.
- Tests do not mock fetch/routes, seed production accounts or use real email.
- All endpoints are loopback. Backend settings require MP_E2E=1 and a database
  named mp_e2e*, refusing remote hosts and non-test database names.
- Parent .env discovery is disabled; SMTP/Zoho/SMS/payments/storage are isolated.
- No browser auth-state, trace, screenshots or video are published as artifacts.
- These two scenarios do NOT cover the entire reception-to-delivery workflow.

Release readiness
The final job requires success from Backend, Frontend, Dependencies, Secrets,
Source security (both languages) and Browser acceptance. Failed, skipped and
cancelled prerequisites do not produce a successful readiness check.
There is deliberately no automatic production deploy command in this workflow.

Local reproduction (PowerShell, from frontend with the test Python environment)
Install backend/requirements-ci.txt and run npm ci, then:
  npx playwright install chromium
  $env:MP_E2E = '1'
  $env:DATABASE_URL = 'sqlite:///mp_e2e_local.sqlite3'
  $env:DATABASE_SSL_REQUIRE = 'False'
  # If Python is not on PATH, set E2E_PYTHON to the test interpreter's full path.
  npm run test:e2e
The harness migrates ONLY its isolated test database and binds ports 8008/3108.
Do not set a production DATABASE_URL. It will refuse remote/non-test databases.
For production-representative runs, use the workflow's PostgreSQL services.

TDD/BDD working agreement
- Before a change, write concrete acceptance examples with the business owner.
- For a bug, first reproduce the failure in an automated test; record the red
  result, implement the smallest fix, then run/refactor with the suite green.
- Keep pricing/RBAC/state transitions mainly in fast unit/API tests; use browser
  scenarios for critical cross-boundary journeys, not every field permutation.
- Given/When/Then scenarios can use pytest and Playwright; Cucumber is not required.
- This workflow cannot certify that a developer wrote a test before implementation.
  Test-first evidence and business acceptance remain review responsibilities.
- A red/green case was exercised for invalid SARIF security scores; gate tests
  also cover missing reports, failed scans, suppressions and severity handling.
