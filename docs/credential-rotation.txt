MP credential rotation: controlled rollout
==========================================
Never copy secrets into chats, source, process arguments or logs. Use Secret
Manager references and private owner entry for Render. The exposed signing key
must NOT be put in Django SECRET_KEY_FALLBACKS or otherwise trusted for JWT/link
verification. Existing sessions/approval links must expire after auth-key rotation.

Compatibility release (safe before activation)
---------------------------------------------
- Without INTEGRATION_ENCRYPTION_KEY, existing email/WhatsApp encryption is unchanged.
- With a dedicated root, new integration writes use that root. A temporary
  INTEGRATION_ENCRYPTION_KEY_FALLBACK can read the previous root for rollout only.
- This fallback has no role in authentication, sessions or signed approval links.
- Zoho's callback is configurable and restricted to approved MP HTTPS callback
  routes. Preserve the currently registered callback until the owner registers the
  stable public-domain callback in Zoho. No unsolicited test mail is sent.

New values are generated privately into Google Secret Manager:
  mp-integration-root:1      -> INTEGRATION_ENCRYPTION_KEY
  mp-django-signing-rotated:1 -> SECRET_KEY
The original mp-django-secret-key:1 is temporarily the integration decryption
fallback ONLY. It must not remain an authentication key after rotation.

Apply only after all writers use the compatibility release and the new settings
------------------------------------------------------------------------
1. Pass full CI for the exact release; deploy compatible code while legacy
   settings remain active. Confirm the deployed release, not merely HTTP 200.
2. Owner privately updates Render's SECRET_KEY, INTEGRATION_ENCRYPTION_KEY and
   INTEGRATION_ENCRYPTION_KEY_FALLBACK in one coordinated update. Cloud Run uses
   the corresponding named Secret Manager versions. Retain credential backups.
3. Run `python manage.py rotate_integration_credentials` (dry-run) on the private
   migration job. It prints counts only and performs no writes/provider calls.
4. Run the same command with --apply from a runtime configured with private GCS
   storage and a writable database connection. It locks integration rows, validates
   every ciphertext, saves an encrypted-only private backup BEFORE any DB change,
   then re-encrypts all legacy fields atomically. Backup failure aborts all changes.
   Names contain no customer identifiers; no plaintext/root values are logged.
5. Run --verify-current-only with the temporary fallback absent. Compare counts
   and verify all configured entries decrypt. Repeated apply is idempotent.
6. Owner removes INTEGRATION_ENCRYPTION_KEY_FALLBACK from Render. Remove the
   fallback binding/configuration from Cloud Run too. Retain the old root only
   under restricted recovery access until the encrypted-backup retention expires.
7. Rotate/revoke the exposed database login in coordination with every consumer.
   Keep the new connection string in Secret Manager and update Render privately.
   Do not reset a possibly shared role without confirming its consumers. Merely
   changing a password does not terminate existing authenticated DB connections.
8. Revalidate private media access, app health, authentication, expired/invalid
   approval-link handling, integrations and callbacks before production cutover.

Recovery
--------
No schema/business-record migration is involved. The private backup contains only
original ciphertext, row IDs and encrypted field names. A restore must be scoped
to that backup and coordinated with integration writers; never overwrite settings
that were changed after the backup without reviewing them. Keep a compatible
release and the necessary root version available for recovery. Do not roll back
to the compromised authentication key. No automatic deletion of old backups or
secret versions is authorized by this runbook.
